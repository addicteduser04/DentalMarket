# Product image egress maintenance

Storefront product and student-pack media is delivered directly from Supabase Storage through `next/image` with `unoptimized`. Vercel therefore provides layout and lazy-loading behavior but does not perform runtime transformations.

## Object convention

Existing originals remain unchanged. Each referenced original may have two immutable siblings:

- `<original-path>.dn-card.webp` — 480 px maximum width, WebP quality 78
- `<original-path>.dn-detail.webp` — 1200 px maximum width, WebP quality 82

Both variants preserve aspect ratio/orientation and are never upscaled. Storefront resolution falls back from the requested variant to the original and finally `/branding/dentanova-product-placeholder.svg`.

## Audit and generation

`npm run images:audit` audits checked-in catalogue references without network access. `node --env-file=.env.local scripts/image-audit.mjs --storage` performs a read-only production metadata inventory; it does not download image bodies or modify Storage.

`npm run images:generate` is a production metadata dry run. Local fixtures can be processed with `npm run images:generate -- --input-dir <input> --output-dir <output>`.

Production selection supports `--limit <n>`, `--paths <comma-separated-paths>`, `--product-ids <comma-separated-uuids>`, and `--manifest <json-file>`. `--inspect --output-dir <directory>` downloads only the selected sources and writes variants locally. It never uploads. Production upload requires `--apply`, `--confirm-production`, and an explicit selector; `--limit` is capped at 50.

The generator skips unjustified variants based on decoded dimensions and source bytes, then also rejects outputs that save less than 10%. A run emits original/generated byte totals, skipped reasons, failures, output paths, `variant-report.json`, and an availability `variant-registry.json`. Existing variants are skipped, uploads use `cacheControl: 31536000` and `upsert: false`, and no original or variant is deleted or overwritten.

The storefront only requests variants listed in `data/product-image-variants.json`. Until verified uploaded paths are added to that registry, it requests the original directly. This prevents repeated missing-variant requests during partial rollout.

## Rollout order

1. Run the metadata audit and save its report.
2. Validate local fixtures and review generated WebP quality.
3. Run a selected production generation dry run and local inspection.
4. Back up/export current product image references.
5. Upload a selected 10–20-image batch with explicit confirmation and review all skipped objects.
6. Verify representative card/detail variant public URLs, then copy only verified entries into `data/product-image-variants.json`.
7. Deploy the resolver and verified registry only after variants exist.
8. Re-run the audit and monitor Supabase Storage egress/cache hit behavior.

Do not broaden product RLS or pack visibility policies. Variant paths are derived only from already-authorized public image URLs and are independent of catalogue visibility.
